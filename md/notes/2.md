### Administrative Policies

Authorizations define ***who can access what***. Administrative policies define who can create, modify and revoke, ***so manage authorizations***.

\bigskip

> ***Types***

- **Centralized:** A privileged user (e.g., an administrator) manages all authorizations; Typical of MAC.
- **Owner-based:** The creator of an object manages the authorizations for that object; Native to DAC.
- **Cooperative (multi-party):** Multiple users must approve changes.

\bigskip

> ***Decentralization Trade-off***

An owner can even ***delegate the administrative privileges*** to other users.

This ***increases the flexibility*** of the administration, but the more decentralized the administration becomes, the ***greater the risk*** of privilege diffusion.

\bigskip

> ***Design Patterns***

A well-designed access control system should follow these ***principles and assumptions:***

- **Least Privilege ("need to know")**: A subject should have only the minimum privileges necessary to perform its task.

- **Maximized Sharing:** Grant a subject all accesses that do not violate integrity and confidentiality of data, as defined the security policies.

- **Closed World Assumption (CWA):** Access is denied by default. If no authorization is specified for an object, access is prohibited.

- **Open World Assumption (OWA):** Access is allowed by default. If no authorization is specified for an object, access is granted.

### Purpose-Based Access Control (PBAC)

*_Purpose-Based Access Control (PBAC)_* is an access control model for relational databases where access decisions depend not only on **who** accesses **what**, but also on **why** the data is accessed. It is a key component of privacy-preserving DBMSs such as Hippocratic DB. 

\bigskip

> ****Purposes****

PBAC addresses three main issues:

- ****Purpose semantics:**** defining what a purpose means.

- ****Data-purpose association:**** associating purposes with data.

- ****Purpose enforcement:**** using purposes during access control decisions. 

\bigskip

> ****Types of Purpose****

- ****Intended Purpose (IP):**** purpose associated with each data item; regulates how the data can be used.

- ****Access Purpose (AP):**** purpose specified when accessing a data item; associated with the query. 

**IP and AP have different roles:**

**IP** → how the data **can be used**
**AP** → how the data **will be used**

\bigskip

> ****Intended Purpose****

An intended purpose is represented as:

$$
IP = \langle AIP, PIP \rangle
$$

- ****AIP (Allowed Intended Purposes):**** permitted uses, derived from user preferences.

- ****PIP (Prohibited Intended Purposes):**** forbidden uses, imposed by organizational requirements or privacy laws.

- ****PIP is optional and overrides AIP.**** 

\bigskip

> ****Purpose Hierarchy****

Purposes are organized in a hierarchical structure.

For a purpose $P$:

- $P^\downarrow$ = **P + descendants of P**

- $P^\uparrow$ = **P + ancestors of P**

- $P^\updownarrow = P^\downarrow \cup P^\uparrow$

The effective set of allowed purposes is:

$$
IP^* = AIP^\downarrow - PIP^\updownarrow
$$

Therefore, a purpose is allowed only if it belongs to the effective set $IP^*$. 

\bigskip

> ****Purpose-Based Authorization****

Users are granted purpose-based authorizations, which can be based on:

- users

- roles

- attributes

An authorization can be represented as:

$$
\langle ap,\ obj,\ r/u\rangle
$$

where $ap$ is the access purpose, $obj$ the protected object and $r/u$ the allowed operation. 

\bigskip

> ****PBAC Enforcement****

Users must explicitly specify the **AP** when issuing a query:

```text
SELECT email FROM Customer FOR Marketing
```

A user $u$ can execute query $q$ with access purpose $AP$ iff:

1. The **authorization base contains a supporting authorization**.
2. The **IPs associated with the accessed data are compliant with AP**. 

**Purpose compliance:**

$$
AP \in IP^*
$$

equivalently:

$$
AP \in AIP^\downarrow
\quad\land\quad
AP \notin PIP^\updownarrow
$$



\bigskip

> ****Enforcement Techniques****

- ****Query Rewriting:**** the query $q$ is rewritten into $q'$ so that it only accesses data whose IPs are compliant with the AP.

- ****Post-processing:**** the DBMS filters from the result of $q$ the tuples whose IPs are not compliant with the AP. 

\bigskip

> ****Why PBAC?****

- Enforces the **purpose limitation principle**.

- Reduces the risk of **secondary data usage**.

- Provides a formal enforcement model for purpose-based privacy policies.

\bigskip

> ****Limitations****

- Purpose definitions can be **ambiguous**.

- Authorization management can be **complex**.

- Query rewriting introduces **overhead**.

## Bell-LaPadula (BLP) Model

Bell-LaPadula (BLP) model is a MAC-based framework designed for maintaining the confidentiality of information by ***restricting access based on security levels***.

\bigskip

> ***Security Levels***

Security levels are organized in a hierarchical structure, with higher levels representing more sensitive information, such as:

$$
TS > S > C > U
$$

That is: **Top Secret (TS)** is the highest level, followed by **Secret (S), Confidential (C), and Unclassified (U)**.

\bigskip

> ***Categories***

Categories are used to further ***refine the classification of information*** within each security level.

Assume to have a subject with a security level of $S$ and categories $\{Alpha, Beta\}$:

$$
S:\{Alpha, Beta\}
$$

\bigskip

> ***READ***

To read an object, ***the subject should dominate the object***. This means that:

$$
L_s \geq L_o \quad \text{and} \quad C_o \subseteq C_s
$$

The **Simple Security Property (ss-property, "no read up")** states that information can only flow ***upwards*** in the hierarchy, meaning that a subject can read an object only if the subject's security level is greater than or equal to the object's level, and the object's categories are a subset of the subject's categories.

\bigskip

> ***WRITE***

To write to an object, ***the object should dominate the subject***. This means that:

$$
L_o \geq L_s \quad \text{and} \quad C_s \subseteq C_o
$$

The **Star Property ($*$-property, "no write down")** states that information can only flow ***downwards*** in the hierarchy, meaning that a subject can write to an object only if the object's security level is greater than or equal to the subject's level, and the subject's categories are a subset of the object's categories.
