# Task 6

## Goal

This task implements Oracle Label Security policies for the Clinical Trial
Management schema. The OLS model protects sensitive rows using labels composed
of both:

- a **level**, representing sensitivity;
- a **compartment**, representing the information domain.

The SQL code is in:

- `app/6/00_create_ols_policy.sql`;
- `app/6/01_create_label_components.sql`;
- `app/6/02_authorize_ols_users.sql`;
- `app/6/03_apply_ols_to_tables.sql`;
- `app/6/04_label_table_rows.sql`;
- `app/6/05_grant_and_check_ols.sql`.

## High-Level OLS Policies

### OLS-P1. Clinical and personal data protection

Clinical study records and participant records are labeled with the `CLIN`
compartment. Participant data can be `CONFIDENTIAL` or `RESTRICTED`.

Users can read a row only when their OLS session label dominates the row label:

- the user level is greater than or equal to the row level;
- the user has the `CLIN` compartment.

This protects:

- `STUDIES`;
- `PARTICIPANTS`;
- clinical documents in `TRIAL_DOCUMENTS`.

### OLS-P2. Regulated, financial and safety material separation

Regulatory submissions, financial contracts and safety reports are separated
with compartments:

- `REG` for regulatory documents;
- `FIN` for financial contracts;
- `SAFE` for safety reports and adverse events.

Examples:

- `CT_REG_BLU` can read `REG` material up to `RESTRICTED`;
- `CT_SPONSOR_LILA` can read `CLIN` and `REG` material only up to
  `CONFIDENTIAL`;
- `CT_AUDITOR_GIALLI` can read all compartments up to `RESTRICTED`;
- users without `FIN` cannot read financial contract rows.

## OLS Policy

The OLS policy is:

| Property | Value |
| --- | --- |
| Policy name | `CT_OLS_POL` |
| Label column | `OLS_LABEL` |
| Default option | `READ_CONTROL` |

`READ_CONTROL` means that row visibility is controlled for read operations.

`CT_OWNER` receives the OLS `FULL` privilege so it can assign row labels.

## Protected Tables

The policy is applied to:

- `CT_OWNER.STUDIES`;
- `CT_OWNER.PARTICIPANTS`;
- `CT_OWNER.TRIAL_DOCUMENTS`;
- `CT_OWNER.ADVERSE_EVENTS`.

Rows are labeled from existing classification columns:

- `STUDIES.SENSITIVITY_LABEL`;
- `PARTICIPANTS.PERSONAL_DATA_LABEL`;
- `TRIAL_DOCUMENTS.CLASSIFICATION` and `TRIAL_DOCUMENTS.DOCUMENT_TYPE`;
- `ADVERSE_EVENTS.SAFETY_LABEL`.

The policy uses one label column per protected table and avoids creating
separate views for every label combination. Access is controlled by label
dominance between the user session label and the row label.

## SQL Execution

Run the scripts in this order:

```sql
-- As LBACSYS or an OLS administrator
@app/6/00_create_ols_policy.sql

-- As a user with CT_OLS_POL_DBA enabled
@app/6/01_create_label_components.sql
@app/6/02_authorize_ols_users.sql
@app/6/03_apply_ols_to_tables.sql

-- As CT_OWNER
@app/6/04_label_table_rows.sql
@app/6/05_grant_and_check_ols.sql
```

Example checks:

```sql
-- Regulatory officer: should see REG material but not FIN rows
CONNECT ct_reg_blu/"LabTask1_2026#"
SELECT document_id, document_type, classification
FROM ct_owner.trial_documents;

-- Auditor: should see FIN and SAFE rows up to RESTRICTED
CONNECT ct_auditor_gialli/"LabTask1_2026#"
SELECT document_id, document_type, classification
FROM ct_owner.trial_documents;
SELECT event_id, severity, safety_label
FROM ct_owner.adverse_events;
```
